# 代码审查修复闭环

执行严格的“实现-审查-修复”循环，只有在质量门禁通过后才可结束。

## 工作流程

1. 明确变更范围与受影响文件。
2. 实现用户需求。
3. 对新增与修改代码做正确性、安全性、可维护性审查。
4. 修复全部阻塞问题。
5. 重新构建并执行针对性验证。
6. 持续重复“审查-修复”，直到无阻塞问题。

## 阻塞问题定义

以下问题一律视为阻塞，必须修复后才能交付：

- 崩溃风险、UAF、空指针解引用、数据竞争、死锁。
- 认证、密钥、SQL、序列化、输入校验等安全缺陷。
- 业务逻辑错误、接口契约破坏、协议不兼容。
- 当前变更引入的构建失败、测试失败、启动回归。
- 异步/协程链路中的超时、生命周期、资源泄漏问题。

## 审查清单

每一轮都要覆盖以下维度：

- 正确性：边界条件、错误分支、降级路径。
- 并发性：所有权、生命周期、线程归属、共享状态。
- 可靠性：超时处理、重试语义、取消安全。
- 安全性：凭据处理、令牌校验、注入风险。
- 兼容性：API/协议字段、配置默认值、迁移路径。
- 可运维性：日志、诊断信息、失败提示、启动前置条件。

## 验证规则

- 每次改动后至少执行一次编译/构建。
- 对受影响模块执行最相关的 smoke/test。
- 先跑窄范围验证，再按需扩大验证范围。
- 不得忽略本次变更引入的失败检查项。

## 输出规范

按以下顺序汇报：

1. 改了什么。
2. 审查了什么。
3. 发现并修复了哪些问题。
4. 执行了哪些验证及结果。
5. 剩余的非阻塞风险或后续建议。

如果阻塞问题暂时无法修复，必须停止并明确说明阻塞点及下一步修复方案。
